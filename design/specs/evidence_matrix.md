# BLACKOUT — Evidence Matrix & Investigation Design

**Owner:** Member 6 (Abubaker) — Game Systems & Content Designer
**Branch:** `member-6/game-design`
**Companion docs:** [`design.md`](../../design.md) §3.5.3/§3.6 (source design intent),
[`task_specifications.md`](./task_specifications.md) (objective mechanics),
`shared/evidence_config.gd` / `server/evidence_manager.gd` (implementation)

This document defines exactly what evidence is generated by which sabotage action, how it is
worded, and the discoverability/discussion rules Crew and UI must follow. It mirrors
`EvidenceConfig.OBJECTIVE_EVIDENCE_TEMPLATES` and `EvidenceConfig.RECOVERY_EVIDENCE_TEMPLATE`
exactly — those constants are the source of truth; this document is the design rationale and
presentation guidance layered on top.

---

## 1. Core Rule: Facts Only, No Attribution

Every `EvidenceDefinition` is serialized to clients via `to_public_dict()`, which **never**
includes a player ID, role, or actor attribution — only what happened, where, and when
(`design.md` §3.6, hard constraint #8 in §5). The Impostor's identity must never be
computable from evidence data alone; it can only be inferred by cross-referencing evidence
against what players *say* they did during the Discussion phase. UI (Member 5) must never
render evidence with a "caused by Player X" label, even in a debug/dev build shipped to
players.

---

## 2. Impostor Objective → Evidence Mapping

Generated once per objective completion by `EvidenceManager.create_evidence_from_objective()`,
deduplicated per objective ID (an objective can only ever produce evidence once). All entries
surface simultaneously to every Crew member the moment `POST_BLACKOUT_INVESTIGATION` begins —
there is no staggered/partial reveal in MVP.

| Objective | Evidence Type | Display Name | Description (exact client-facing text) | Location | Severity | Category |
|---|---|---|---|---|---|---|
| `steal_confidential_files` | `classified_files_missing` | Classified Files Missing | "Classified research files are missing from the Executive Office file storage." | `executive_office` | high | espionage |
| `extract_orion_core_data` | `orion_core_data_extracted` | ORION Core Data Extracted | "ORION core terminal logs indicate unauthorized research data was extracted." | `orion_core` | critical | data_theft |
| `disable_orion_containment` | `orion_containment_disabled` | ORION Containment Disabled | "The ORION core containment field was manually overridden and deactivated." | `containment_hub` | critical | containment |
| `sabotage_generator` | `generator_sabotaged` | Generator Sabotaged | "Main power generator distribution cables were severed, causing primary grid collapse." | `generator_room` | critical | sabotage |
| `tamper_security` | `security_tampered` | Security Feed Tampered | "Security surveillance console audit logs show scrambled camera feeds and altered history." | `security_room` | high | security |

**Reading guidance for players:** severity is a presentation hint (Member 5 can use it for
icon/color weight — e.g. `critical` = red siren icon, `high` = amber, `info` = neutral), not a
guilt score. A `critical` entry is not "more suspicious," it just describes a more severe
facility-impact event; three `critical` entries and zero `high` entries is an entirely possible,
non-anomalous match outcome since only 3 of the 5 objectives are assigned per match (see
`task_specifications.md` §3).

## 3. Recovery Completion Evidence

Generated once per recovery system completion by
`EvidenceManager.create_evidence_from_recovery()`, deduplicated per system ID.

| Source | Evidence Type | Display Name Template | Description Template | Severity | Category |
|---|---|---|---|---|---|
| Any of the 4 recovery systems (§4 of `task_specifications.md`) | `recovery_system_restored` | `"{System} Restored"` | `"Subsystem '{System}' was restored to operational status by maintenance protocol."` | info | recovery |

This is intentionally low-severity, informational evidence — it exists so the Investigation
list shows the *full* picture of what happened during the blackout (not just sabotage), letting
Crew reconstruct a rough timeline of "what got fixed vs. what stayed broken," which directly
supports the fake-repair deduction pattern described in §5 below.

## 4. Reserved Evidence Types (Defined, Not Yet Wired to a Trigger)

`EvidenceConfig` also defines two general-purpose evidence type keys that
`EvidenceManager.create_environmental_evidence()` can emit, but no current caller in
`server/impostor_objective_manager.gd` or `server/blackout_manager.gd` triggers them yet. They
are documented here as the design-intended hooks for the secondary sabotage actions called out
in `design.md` §3.5.3 (fake repairs, evidence relocation, generic tampering) that did not make
the Step 7 objective catalog:

| Evidence Type | Suggested Trigger (Recommended, Not Yet Implemented) | Suggested Severity |
|---|---|---|
| `unauthorized_restricted_access` | Impostor enters a restricted room (Office/Executive Office, ORION Core Chamber, Containment Hub) during `BLACKOUT_ACTIVE` without completing an objective there — e.g. they scouted the room but were interrupted. Gives Crew a near-miss data point even when an objective fails/is abandoned. | medium |
| `system_damage_detected` | **Fake-repair tell:** a player publicly claims (via chat, out of scope for server validation) to have completed a recovery system that the server's `recovery_systems` dictionary still shows as incomplete. This is the mechanical basis for the "Player 3 said they repaired Security, but it's still damaged" pattern in `design.md` §3.6 — currently the *detection* of the lie is entirely player-memory-driven (comparing chat claims against the recovery `X/Y` broadcast), since the game does not track "who claimed what." No server change is required to support this pattern today; this row documents it as an intentional, already-supported emergent mechanic rather than a gap. | high |

**Recommendation for Member 2 (backend) / Member 8 (QA):** if a future sprint adds explicit
secondary sabotage actions beyond the 5-objective catalog, wire them to
`create_environmental_evidence()` using the type keys above rather than inventing new evidence
type strings, to keep severity/category conventions consistent.

## 5. Discovery & Discussion Design Rules

1. **Simultaneous, full reveal.** `EvidenceManager.finalize_investigation()` broadcasts the
   entire accumulated evidence list at once when `POST_BLACKOUT_INVESTIGATION` begins. There is
   no "search the room to find it" interaction in MVP — evidence is a facility-wide alert feed,
   not a hidden-object hunt. (A room-based discovery mechanic is an explicit non-goal for MVP;
   revisit post-MVP if playtesting shows the feed feels too passive.)
2. **No evidence without action.** If the Impostor never completes an objective and never
   triggers a recovery system, the investigation phase can legitimately show zero or very few
   entries. Silence is itself information ("nothing detectable happened" narrows suspicion less
   than it might seem, since an efficient Impostor produces minimal footprint by design).
3. **Evidence never expires or hides.** All evidence persists for the rest of the match
   (through Meeting, Voting, and Meltdown) — Crew should be able to reference it during
   discussion at any point, and UI should keep it accessible, not just flash it once.
4. **Location and category, not player position history.** Per PRD FR-29, the system must not
   surface "who was near which room" — evidence's `location_id` tells Crew *where* something
   happened, and players must supply the "who was there" half themselves from memory/claims.
5. **Cross-referencing is the whole game.** UI/UX (Member 5) should present evidence in a way
   that invites comparison against players' own chat claims (e.g., a persistent side panel
   during Discussion, not a one-time popup), since the entire Investigation → Meeting flow
   depends on players connecting "Security Feed Tampered" evidence with "I saw Player 4 near
   Security" testimony themselves.
